# 需求 ↔ 素材对应表（方案，2026-10-07）

## 目标

- 每个需求场景绑定一组素材（同一测试的变体都算），由人确认；素材侧能反查自己对应哪些需求条款。
- “是不是同一个测试、要改什么”交给 LLM 提建议、人拍板；规则只负责找候选、列证据。
- 不再追求“正确素材排第一”：素材同质化严重，锁定那一族就够。

## 流程

1. **找候选**：沿用批量匹配（名字/条款号 + 文本 + 结构召回），每个场景从前 3 放宽到前 10。
2. **LLM 判断**：每个需求场景一次调用，场景之间并行。
   - 输入：需求原文（场景正文 + 它引用的条款）和抽取出的结构；每个候选的名字、素材故事（`asset_story`）、
     现有比对列出的差异（只列，不分级、不算成本）。
   - 输出（JSON）：每个候选判“同一测试 / 同一测试但要改（改什么，一两句）/ 不是 / 拿不准”；
     把只差数值的变体（速度、TTC、天气、时段、车型）归成一组，标一个首选；名字和文件内容冲突时写出来。
   - 规则：不能只凭名字判“同一测试”，要能从故事或差异里找到依据。
3. **人确认**：批量表每个场景显示 LLM 建议的那一组和状态，一键接受、改选，或标“没有素材”。
   可以“接受全部‘同一测试’的建议”。没确认的不进对应表。
4. **存对应表**（工作区一份，跨项目）。每条记：
   - 需求：文档（PDF sha256）、条款号、场景标题、场景修订号；
   - 素材：asset_id + 绑定时的 version_id，首选标记；
   - 状态：直接用 / 要改（改什么） / 没有素材；来源（LLM 建议、人工确认）和时间。
5. **反查和覆盖**：
   - 素材详情加一栏“对应的需求条款”；
   - 概览页按文档显示：多少条款有素材、哪些条款没有素材、哪些素材没被任何条款用到。
6. **跟版本走**：素材出了新版本，或需求场景被改过（修订号变了），对应条目标“待重核”，不自动改。

## 和现有功能的关系

- 保留：PDF 抽取、结构比对（找候选、列差异）、素材故事、批量匹配、版本钉住、报告导出。
- 现在的“保存决定”（每个场景选一个素材出报告）改为同时写进对应表；报告照样能导出。
- 降级：5 级判级和成本数值不再是界面上的主结论，先留在后台做排序；
  “按修改工作量分四档”和“被测功能”的细节讨论先停，等 LLM 判断的效果出来再看要不要。

## 怎么衡量（先离线跑，不动界面）

用三份有真值的标准（本地评测，不进仓库），每份看四个数：

- **召回**：正确那一族在不在前 10 名候选里；
- **选对率**：LLM 选的那一组里有没有正确素材；
- **错绑率**：LLM 说“同一测试”，但选的那一组里没有正确素材；
- **拿不准率**：LLM 说“拿不准”的比例，这些要人看。

再跑一遍隐去素材名的版本，看 LLM 有多依赖名字（别的库名字可能起得不好）。
基线：之前盲审（只给故事、不给名字），有真值的 33 个场景选对 31 个。

## 已定（2026-10-07）

1. 一个需求场景可以绑多个素材（同族变体），其中标一个首选。
2. 对应表放全局（跨项目，方便管素材）。
3. LLM 的建议必须人点确认才进表。
4. 名字用来找候选、给 LLM 当线索，但不能只凭名字绑定，由人确认兜底（改变 2026-10-05“素材名不用于推断”）。
5. 先离线试 LLM 判断：已做（`binding_judge.py`），候选池扩为“综合排名、规则、名字、结构、标题”五路取并集；
   在本地三份有真值的标准上，LLM 首选明显好于现排名第一，隐去素材名也一样（数字只留在本地评测记录）。

## 已做进工作台（2026-10-07）

- **找候选**（`binding_suggest.candidate_pool`）：综合排名前 10 ∪ 规则前 10 ∪ 名字前 5 ∪ 结构文本前 5 ∪ 标题前 5
  （需求标题与素材名的中文两字片重合，去掉括号注、数字和字母），平均约 20 个；与离线试验的候选池逐场景一致。
- **模型判断**：打开 PDF 即为条款复用评估，“生成复用建议”启动后台任务（每个项目一个，可同时选多份 PDF，场景之间并行，并发数取模型设置）；
  回复按请求缓存，只缓存对得上候选的回复，没变的场景再建议不再调用模型。建议存在 `bindings/suggestions/<PDF sha256>.json`。
- **问 3 次、用最深的思考**：每个场景独立问 3 次（并行），思考等级取模型清单里最深的一档（DeepSeek：max），
  回复被截断时这一次改用模型默认的一档再问；没有等级清单的服务照模型设置。建议取 3 次里被选得最多的首选，
  用最早给出它的那一次的组、判断和理由。3 次首选都一样标“一致 3/3”，不一样标红色“不一致 2/3”（提示里列出别的几次选了什么）。
  本地三份标准上试过：max 比默认的 high 首选更准、更稳，3 次一致时首选全对；代价是每次调用慢约 3 倍。
- **四档结论**：模型建议和人工结论共用四档：直接复用、修改复用、不适用、无法判断（“无法判断”只出现在建议里）。
  人工确认的结论在素材前带绿色对勾（悬停显示“采纳模型建议”或“人工指定”和时间），表格上方有图例。
- **人确认**：每行“采纳”，右侧详情可改选一组素材、首选和结论（直接复用 / 修改复用 + 修改内容 / 不适用）；
  “采纳全部一致的‘直接复用’建议”只采纳还没确认、3 次一致的行；不一致的要人逐条复核。已确认的行不再显示“采纳”，
  除非条款事实或素材变了需要重新确认。“手动检索”可在规则排序和逐项比对里自己挑素材并“采用为本条款的复用素材”。
- **复用结论存储**：`bindings/bindings.json`，所有项目共用；需求键 = PDF 内容 + 条款号 + 抽取时的标题（第 1 版，之后改标题不变）。
  采用的素材版本像报告一样钉住（不能删）。条款事实改了、或采用的素材出了新版本 → 标“待重新确认”，不自动改。
- **导出**：“导出复用评估表”把当前所看 PDF 的全部条款导成 CSV（带 BOM，Excel 直接打开）或网页；未确认的条款列出模型建议和一致性。
- **反查和覆盖**：素材详情“关联条款”页列出采用它任一版本的条款；总览页按 PDF 显示可复用 / 不适用 / 待确认 / 待重新确认，
  以及未被任何条款采用的素材。

## 规则的角色

规则继续负责读文件（素材故事、差异）和找候选：名字起得不好的库只能靠它找候选，LLM 读的故事也全靠它。
判级的细分（5 级、成本数值、核心/可调）不再是主结论。

## 工况（2026-10-09，第 1 步：抽取）

一个条款常规定几次搭建不同的试验：参数表的每一行、日间和夜间、按被试车辆选一个的分支（车速区间对应的限速牌、
M1 / 非 M1 的结束 TTC、厂商声明的雨雾等级）、分别用几种目标物、预试验。以前这些只存成结构里的一串值
（如限速 [40, 60, 80, 100]），日间/夜间只能存一个；对应表只有“一组素材 + 首选”，说不出哪个素材对应哪次试验。

- **读法**（`pdf_v2/scene_variants.py`，`scene_first.read_variants`）：每个场景单独问一次模型，读的原文和结构那一步相同；
  输出维度（名称、种类、都要做 / 按被测车选一 / 任选一、原文引句）和工况清单（短名 + 每个维度的取值）。
  只有一次试验的场景输出空。每个场景独立问 3 次，工况数取多数（没有多数取中位），不一致的标“请核对”；
  引句在本场景原文里找不到的维度标“请核对”，不删。
- **不算工况**：误差和区间、重复次数、一次试验里的先后步骤、评分和测量、被试车辆自身的设置、试验地点和开放道路的路线时段、
  厂商自定且原文没给值的参数、举例。
- **评测**：在两份标准上按人工标的工况数核对，再在没调过提示词的第三份上检验一次（数字只留在本地评测记录）。
- **存放**：导入 PDF 时结构读完就读工况（同一个模型缓存），存在文档目录的 `variants.json`（按场景 id，读不出的场景记空），
  不进场景的事实：已确认的对应不会因此变成待重新确认，改场景也不影响工况。
- **补读**：服务启动时，读工况之前导入的文档（和有场景没读出的文档）在后台补读，每个项目一个任务，期间项目不能改名或删除。
  从 `extraction.json` 里的章节和场景还原，不重抽、不改结构；已读过的走缓存不花钱。没填模型 Key 就不补读。
  提示词换版本不会自动重读。
- **还没做**：第 2 步按工况分配素材（数值吻合帮排序、复用建议说出每个素材对应哪个工况）；第 3 步界面（主行展开工况子行）。
